# 0009. 코드 관리 값은 이름 대신 코드로 저장한다 — 예적금 은행 · 구독 결제수단

- **상태**: 채택
- **결정일**: 2026-10-20
- **기록일**: 2026-10-20
- **결정 방식**: AI 가 대안 2~3개와 장단점 · 추천을 보여 주고, 운영 데이터를 확인한 뒤 사용자가 골랐다 (둘 다 AI 추천안). 소급 기록이 아니다

## 맥락

- 코드 관리(`category` 테이블, 설정 > 코드 관리)는 선택박스 항목을 도메인별로 둔다. 각 행은 `code` · `label` · 순서 · 사용 여부를 가진다.
- 기록에 무엇을 저장하는지가 도메인마다 달랐다.
  - 가계부 카테고리 · 결제수단 · 입금 은행: **code** 를 저장하고 화면에서 label 로 바꿔 보인다.
  - 예적금 은행(`saving.bank`): **label** 을 저장했다. 선택지는 코드 관리에서 읽었다. 그 전에는 자유 입력 칸이었다.
  - 구독 결제수단(`subscription.pay_method`): **label** 을 저장했다. 선택지는 프론트 고정 5개였다(`쿠페이` 는 코드 관리에 없음).
- label 을 저장하면 코드 관리에서 이름을 바꿔도 기존 기록은 옛 이름 그대로 남는다.
- 2026-10-20 프론트 전체를 점검하다 드러났다. 같은 날 구독 카테고리 · 예적금 · 투자 유형 · 가계부 비활성 항목도 코드 관리를 따르게 고쳤다(`0be6503` · `2e08157` · `67de458`).

## 결정

예적금 은행과 구독 결제수단도 **code 를 저장**하고 화면에서 label 로 보인다. 선택지는 코드 관리의 사용 중인 항목 + 그 기록의 기존 값(비활성이어도)이다.

- 운영 데이터 (2026-10-20 확인): 예적금 4건의 은행이 모두 코드 관리 목록에 있었다. 구독 3건의 결제수단은 모두 `신한카드` 였다.
- 그래서 이름 → 코드 변환에서 남는 값이 없다.

### 비교한 대안 (결정 때 보여 준 것)

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 이름 저장 유지 (구독은 선택지만 코드 관리에서) | 프론트만 수정, DB 변경 없음 | 코드 관리에서 이름을 바꾸면 기존 기록은 옛 이름. 가계부와 방식이 다르다 |
| **B. 코드 저장으로 통일 (채택)** | 이름 변경이 모든 기록에 반영. 가계부와 같은 방식 | 기존 데이터 변환 SQL · 백엔드 · 데모 시드 수정이 필요 |
| C. 그대로 둠 (구독 결제수단만) | 할 일 없음 | 코드 관리와 계속 따로 논다 |

AI 가 B 를 추천한 이유 (결정 때 보여 준 것, AI 작성):

- 구독 결제수단: 구독 수가 적어 바꾸는 부담이 작다. 나중에 구독 결제를 가계부와 이으려면 코드가 같아야 한다.
- 예적금 은행: 운영 값이 모두 목록 안에 있으면 B 가 깔끔하다.

사용자가 이 추천에 덧붙인 이유는 없다.

## 남은 예외

- **계정 카테고리(`credential.category`)는 label 을 저장한다** — 2026-10-20 계정 카테고리를 엑셀 분류로 바꿀 때 AI 가 제안했고, 사용자가 대안을 고르지 않고 "추천해줘" 로 맡겨 그대로 채택했다 (AI 제안 채택).
  - 이유 (AI 작성): 계정 엑셀 가져오기 · 내보내기 · 검색 필터가 셀 값을 그대로 쓴다.
  - 같은 위험(코드 관리에서 이름을 바꾸면 기존 계정과 끊김)이 남아 있다.

## 다시 정한다면 — 본인 작성

> *AI 초안 (2026-11-02, 본인 요청으로 AI 가 씀) — 본인 판단이 아니라 기록을 보고 쓴 것이다. 읽고 고치거나 지운다.*

**한 줄**: 같은 선택이다 — 이름을 바꿔도 모든 기록에 반영되고 가계부와 방식이 같아진다. 남은 구멍은 코드 관리에서 행을 삭제할 수 있다는 점이다.

### 질문과 답

- **코드 관리에서 행을 삭제하면 그 code 를 가진 기록은 어떻게 보이나? 삭제를 막아야 하나, 비활성만 허용해야 하나?**
  `category.service.ts` 의 `remove` 는 참조 검사 없이 그냥 지운다. 코드 주석도 "삭제 시 라벨만 사라짐, 숨김은 `is_active=false` 권장" 이라 적었다. 기록은 code 문자열만 갖고 있어 이름으로 바꿔 보일 수 없다. 화면에서 구체적으로 어떻게 보이는지는 확인하지 않았다. 막을지는 판단이 필요하다 — 막으려면 도메인마다 참조하는 테이블 여러 곳을 세어야 해서(FK 가 없다) 비용이 있다.
- **계정 카테고리도 code 로 바꿀 가치가 있나? 엑셀 가져오기 · 내보내기에서 무엇을 바꿔야 하나?**
  이름을 바꿀 일이 잦지 않으면 가치가 작다. 현재 label 저장의 이유가 엑셀 셀 값을 그대로 쓰기 때문이다(ADR 「남은 예외」). code 로 바꾸면 가져올 때 label 을 code 로, 내보낼 때 code 를 label 로 바꾸는 변환이 필요하다. 엑셀 처리 코드를 열어 보지 않아 정확한 수정 범위는 확인하지 않았다.
- **백엔드가 저장할 때 code 가 코드 관리에 있는지 검사하지 않는다. 검사하면 무엇이 좋아지고 무엇이 불편해지나?**
  좋아지는 것은 오타 · 삭제된 code 가 저장되지 않는 점이다. 불편해지는 것은 비활성이거나 이미 목록에 없는 기존 값(마이그레이션이 "목록에 없는 값은 그대로 둔다")을 가진 기록이 수정 때 거부될 수 있고, 엑셀 가져오기에서 모르는 값을 만나면 실패 처리를 정해야 한다는 점이다. 선택지가 프런트 선택박스 한정이고 사용자가 1명이라 지금은 없어도 문제가 드러나지 않았다.
