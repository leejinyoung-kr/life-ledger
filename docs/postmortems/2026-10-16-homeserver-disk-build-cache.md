## 요약

두꺼비집을 내렸다 올려 홈서버가 꺼졌다 켜졌다. 재부팅 뒤 점검에서 서비스는 모두 정상이었지만,
디스크가 **232G 중 185G(84%)** 를 쓰고 있었다. 들여다보니 그중 **165G가 docker 빌드 캐시**였다.

앱 네 개가 main 에 push 할 때마다 홈서버에서 이미지를 새로 빌드한다. 빌드할 때 생기는 캐시를
지우는 단계가 어디에도 없어서 943개가 쌓였다. 실제 데이터(DB 볼륨 7개)는 0.24G 뿐이었다.

수동으로 정리해 24G(11%)로 줄였고, 배포 워크플로 끝에 **캐시를 20GB 까지만 남기는 정리 단계**를 넣었다.

## 영향

- **서비스**: 없음. 정리 중에도 떠 있는 컨테이너는 영향을 받지 않았다
- **데이터**: 없음
- **부작용**: 정리 직후 첫 배포는 캐시가 없어 앱마다 몇 분씩 더 걸렸다 (`pnpm install` · 컴파일 · 베이스 이미지를 다시 받음)
- **그대로 뒀다면 (추정)**: 열흘 남짓에 165G 가 쌓였으니 하루 15G 안팎이다. 남은 37G 는 배포가 몰리면 **2~3일**이면 찬다. 디스크가 차면 일어날 수 있는 일:
  - MariaDB 쓰기 실패 → 앱 저장 오류
  - 새벽 DB 백업 실패
  - 배포 빌드 실패 (이건 오히려 알아차리기 쉬운 쪽)

## 근본 원인

직접 원인: 배포 워크플로가 `docker compose build` 만 하고 **빌드 캐시와 태그가 떨어진 옛 이미지를 지우지 않았다.**
docker 가 알아서 지워 주는 양으로는 165G 까지 쌓이는 것을 막지 못했다.

### 5 Whys

1. **왜 디스크가 84% 였나?** → docker 빌드 캐시가 165G 쌓였다.
2. **왜 캐시가 쌓였나?** → 앱 네 개가 push 마다 홈서버에서 이미지를 빌드하는데, 정리하는 단계가 없었다.
3. **왜 정리 단계가 없었나?** → 배포 워크플로를 AI가 "빌드 → 띄우기 → health 확인" 까지만 만들었고, 리뷰 없이 그대로 채택했다.
4. **왜 열흘 동안 아무도 몰랐나?** → 디스크 사용량을 보는 알람이 없다. `/health` 는 앱이 응답하는지만 본다.
5. **왜 알람이 없나?** *(진짜 근본 원인)* → 홈서버를 띄울 때 "서비스가 뜨는가" 만 완료 조건으로 삼았고, **"계속 돌아가는가"(디스크 · 메모리 · 백업 성공 여부)는 확인 항목에 없었다.** 이번에도 정전이라는 우연이 없었으면 디스크가 찬 뒤에야 알았을 것이다.

## 잘된 점

- 재부팅 뒤 점검을 한 번 돌린 덕에 우연히 봤다
- 원인을 크기별로 쪼개서(캐시 · 이미지 · 러너 · 앱 · DB 볼륨) 지워도 되는 것과 아닌 것을 먼저 갈랐다. 실제 데이터는 0.24G 라 지우는 쪽이 안전했다
- 재발 방지를 "기간 기준(7일 지난 캐시 삭제)" 대신 **"크기 상한(20GB)"** 으로 바꿨다. 기간 기준은 배포가 몰린 주에 다시 100G 넘게 쌓일 수 있다
- 정리 단계를 배포 잠금(`/tmp/deploy.lock`) 안에 넣어 다른 앱의 빌드와 겹치지 않게 했다
- 새 앱도 같은 단계를 넣도록 홈서버 규칙 문서(infra README)에 적었다

## 아쉬운 점

- **감지가 우연이었다.** 알람이 없는 것이 진짜 문제인데, 이번 조치는 원인(캐시)만 막았다
- 같은 패턴(배포마다 무언가 쌓인다)이 다른 곳에도 있는지 보지 않았다 — 예: 컨테이너 로그, `~/backups` 의 덤프, 러너 작업 폴더(`~/runners` 4.0G)
- 처음 정리 명령(`docker image prune -a`)이 쓰지 않던 베이스 이미지까지 지워 첫 배포가 느려졌다. 미리 알려 두긴 했지만 피할 수 있었다
